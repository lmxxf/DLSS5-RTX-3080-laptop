# PTX V2.4：四靶子隔离验证，推荐仅启用 C

**推荐按需交错解包＋死亡操作数寄存器池（mask=8）**。A、B 均已实现且逐位等价，但未获得稳定的增量帧收益；D 继续保留 V2.3 hot255，不因消除 spill 就默认放宽 cap。

## 正式结果

每进程 **50 warmup / 80 iter**，三档正向 ABBA / 反向 BAAB。以下为四次进程 GPU median/min 的均值，不是所有帧混池 median。

| 输入 | 同轮 V2.3 median | V2.4 median | 耗时下降 | 正向 / 反向 |
|---|---:|---:|---:|---:|
| 1280×720 sky | 6.24900 ms | **6.20100 ms** | **0.768%** | 0.680% / 0.854% |
| 1600×900 scene | 9.12850 ms | **9.09175 ms** | **0.403%** | 0.276% / 0.527% |
| 1920×1080 scene | 12.20700 ms | **12.02650 ms** | **1.479%** | 2.010% / 0.949% |

收益较小。1080p 的 GPU min 均值 **11.72350→11.72300ms，基本不变**。默认 DVFS，无锁频；不能把本轮绝对值与上一轮历史 6.13/8.93/11.68ms 直接横比。

18 次快验＋120 次因素对照＋96 次 cap 对照＋24 次条件组合对照，合计 **258 次运行末帧严格 0 bit-diff / maxabs=0 / PSNR=∞ / nonfinite=0**。另有16次 NVAPI 逐核诊断，末帧同样0bit。10项既有回归通过。[完整因素/条件/cap表](results.md) · [验收](validation.json)

## A：FP8_UP 的 7→5 条，正确但未进默认

独立 `cvt.rn.f16x2.e4m3x2` 的 helper 改成 `prmt 0x9180`、`and 0x017f017f`、`shl 7`、装 scale、HMUL2，独立转换只声明 scale。全网4,744处名义少9,488条PTX；共同外层u16→u32扩展未计入7/5。GPU16,777,216组，穷举全部u16及高位干扰，含非有限/符号，0bit。

单因素三档耗时下降 **0.069% / -0.221% / 2.283%**，900p与部分方向不稳定。真实40活跃核名的静态SASS合计183,792→181,914（-1,878），不是把所有导出PTX的9,488直接当动态节省。代码可通过mask1复现，默认关闭。

## B：偏置合并和1,688对四字节融合，正确但未进默认

- 偏置合并 `0x603f603f`，保留原 clamp/round/sign；当前helper实际 **20→19** 条（任务单21→20是另一种计数口径）。每半槽最大和0xbf40，不会向邻槽进位。两位置共33,554,432组GPU输入、所有half位型，含±0/子正规/NaN/Inf，0bit。**40活跃核静态SASS总条数完全不变**；编译器已吸收这类PTX算术变形，不能由省1条PTX推断性能必升。
- 全网7,540个泛型 `mov.b32 {rs,rs}` 不是7,540个可融合对。检查同基本块、函数根作用域、两次FP8_DOWN各自唯一def且只被此mov消费；实际 **1,688对**：FB01 456、FB02 616、FB03 616，覆盖3,376个DOWN。其余含重复广播或不满足消费者/定义条件，不强并。
- 融合使用共享常数、两个分离norm输出及 `prmt 0x6420`；两次源读取仍留在原转换位置，支持安全的非相邻转换，不跨基本块。理论每合格对少7条PTX。另33,554,432组GPU quad对照0bit。[原语](primitives.json) · [资格计数](codegen-audit.json)
- 偏置单因素三档 **-0.080% / -0.337% / 0.627%**；偏置＋quad为 **0.024% / 1.020% / 0.093%**，均有方向变号，不默认启用。

## C：默认保留，声明峰值下降不等于物理spill消失

先计算每个输入的first/last use，每条原FP8 MMA前按需解包，仍按原顺序发两条偶奇K16 MMA；last_use后归还临时pair。若某源或mapped FP16别名会被更早的MMA写坏，则提前到首次覆写前保存，**保持原upfront读取run入口值的语义**，不能仅看第一次使用位置。

| FB | 原临时b32声明峰值 | 池化后 |
|---|---:|---:|
| 00 | 64 | 40 |
| 01 | 80 | 56 |
| 02 | 80 | 56 |
| 03 | 96 | 56 |
| 04 | 160 | 112 |
| 05 | 128 | 80 |
| 06 | 144 | 20 |

64-MMA长run、128warps随机输入、普通和mapped累加器别名覆写两种GPU测试均0bit；整网三档也通过。静态活跃SASS183,792→183,651，仅少141条，主要是调度/生命周期改写，不是宣称动态指令大幅减少。

**物理资源反例须保留**：全导出FB01 STACK **192→224B**、LDL+STL **477→507**；FB04 STACK **96→88B**、LDL+STL **125→127**；FB05仍16B（该上限包含非活跃导出变体），其余FB00/02/03/06为0。不能把较少的虚拟声明当成硬件零spill。[资源](resources.json) · [SASS](sass-audit.json) · [别名风险GPU测试](pool-test.json)

## 条件组合：ABC整体赢，但AB增量不稳定

ABC相对V2.3三档均值收益 **0.955% / 0.927% / 1.374%**，两方向都赢。进一步直接把 **ABC 对 C** 配对：720p +0.357%且两方向同号；900p +0.202%但正反为 **+1.548%/-1.152%**；1080p +0.523%但正反为 **+2.002%/-0.950%**。没有把C的收益冒充A/B的增量收益，最终选C而不是堆满全部开关。所有样本保留，无删样本挑结果。

## D：12个单FB cap控制，未进默认

在ABC基础上隔离FB01/02的192/224/255，以及FB04/05的168/192/224，共12个控制；每控制1080p正反ABBA/BAAB，50/80，全部0bit。

**C64“提高cap不降Occupancy”的前提被本机API否定**：活跃C64静态Shared为4096B，CUDA occupancy API给出的**理论最大驻留**为168 cap下 **12 warps/SM**，192/224/255下 **8 warps/SM**。它不是硬件动态occupancy计数。255清零活跃C64 spill，却使整帧慢 **0.759%**（两方向均慢）；192/224也慢。不是免费的寄存器扩容。

- FB02 255只见0.087%表观median差，min变慢，且理论驻留从12降8，无可靠净收益，保留168。
- FB04 168/192/224对应活跃最大STACK 640/240/152B（ABC255为88B）；168整帧慢6.723%，224收益方向变号，保留255。
- FB05 168把部分核理论驻留提至12 warps，却产生最高176B活跃STACK，整帧慢4.219%；192收益方向变号、224回退，保留255。

逐FB诊断另外跑了 **16个**50/20捕获，复用V2.3的82次单核NVAPI链硬件时间戳。FB01 cap255对应FB01约1.316ms（ABC起始约1.221ms）；FB04 cap168对应FB04约1.880ms（ABC约0.922ms）；FB05 cap168对应FB05约3.575ms（ABC约3.207ms）。这些捕获非ABBA且插桩扰动调度，决策仍以未插桩配对为准。[逐FB表](profile-results.md) · [occupancy与spill](caps-resources.json)
