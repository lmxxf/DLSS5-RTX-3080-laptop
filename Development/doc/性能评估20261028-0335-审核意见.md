# 《性能评估20261028-0335》审核意见

结论：第一、二节主数据基本准确，第三节的单核实验方向值得做；但把旧失败“完全归因于两个重核”不成立，忽略有限 Grid 波次是最大的性能推断缺口。“差几个寄存器”也不能预测 spill。V2.8 已逐核编译并用 CUDA API 查询，目标驻留均可达，但收益必须看同轮整帧对照。

原报告不改。核验数字、源文件 SHA、逐核编译资源和 Grid 计算见[审核核验 JSON](性能评估20261028-0335-审核核验.json)；本轮最终配对结果见 [v28/README.md](../ptx-patcher/v28/README.md)。

## 1. 第一节：性能表正确，运行计数与 STACK 顺序需写清

三档配对均值、耗时下降以及正反方向数字均与 `v27/selected.json` 一致。6.022/8.77950/11.50375ms 是每档四个进程 GPU median 的均值，表前已交代，合理；不能拿它们直接与异轮V2.6历史值相减。

“每进程50/80，170次运行”容易让读者以为170次全是正式计时。实际为 **160次50/80正式运行＋10次1/1快验**；推荐四核方案对V2.6的主表是24次（3档×8），其余是负结果和条件对照。170次末帧0bit/finite结论正确，但仅针对这些测试输入。

六个C32的REG、static Shared以及API理论8 warp结果正确。cap192/184不升、168升至12也有实测。正文先按pre/out/ds/inp排列，随后“STACK分别0/8/8/16”却采用另一顺序，建议直接写 **pre=0、inp=8、ds=8、out=16B**。API验证的是可驻留CTA上限，“受子分区寄存器分配粒度约束”可作为解释，但现有API结果本身没有独立证明具体物理分配机制。168是已测的成功cap，并不表示整个整数范围中唯有168可达12 warp。

C64 cap192最大活跃STACK96→48B、12→8 warp及三档变慢0.38%～0.47%均有证据。二进制大小266,414,592B＝254.0727539MiB，254.07MiB正确。

## 2. 第二节：主体账本正确，两处合并行有微小算术偏差

逐行对 `v27/profile-summary.json` 的原始精度重新求和/相减，16行中的14行全部落在六位小数四舍五入容差内。两条FB06+13+14合并行建议改为：

|档位|V22|V24|V26|V22−V26|V24−V26|
|---|---:|---:|---:|---:|---:|
|720p|0.125491|0.123827|**0.124467**|**+0.001024**|**−0.000640**|
|1080p|**0.262938**|**0.267264**|0.260224|**+0.002714**|**+0.007040**|

误差约1ns量级，不改变结论，但应从原始精度统一舍入，不叠加已舍入子项。核区间合计正确。这是新同轮V22/V24/V26的插桩账本，**不是V27逐核账本，也不是未插桩整帧时间**；建议在表后再明确。V24→V26“单步差”表示选定版本间变化，并不能把每个模块的小幅差值全部归因于某条指令（每档仅两次捕获，DVFS和插桩仍在）。FB02/720回退、FB05/1080回退保留得正确。

非mapped峰值56/56/56/112/80及24+4、48+8、32+8对组成，与逐run审计一致。单位是**静态run内唯一encoded寄存器事件/同时存活对**，不是每帧动态次数，也不是物理kernel REG。FB05“4项及16项合流”应注明：4是直接pack_multidef拒绝项，16是追溯后global＋local quantization混合来源的事件，两个不同统计维度不能加成20个独立优化机会。参数根+16/+24不能单凭加载指令认定是权重；报告没有再次一律叫权重，这点正确。

## 3. 重大因果修正：整包失败不是只有两个重核 spill

`v24/caps-resources.json` 明确显示旧FB05全包168时，除attention176B外，**qkv64B、expand chained160B、publish168B**同样spill。旧FB04全包168除qkv640B外，还有proj_outview168B、ffwd_proj208B、ffwd_proj_inpview208B、ffwd_inpview160B。

因此“完全是因为qkv/attention”既不是旧表支持的事实，也不能从多核同时改变的整帧实验识别。旧4.219%/6.723%回退基于V2.4阶段ABC配置，不是V2.7。应改为：**重核spill是候选解释之一；按核隔离可避免连带改动，但不保证其他核有收益。** 本轮受保护的qkv_512、ffwd_512、attention及projection的SASS保持逐指令相同。

## 4. 动态 Shared 没卡住台阶；有限 Grid 却削弱了台阶的意义

`v23/profile.json` 两档82次发射的dynamic_shared均为0，V27阶段四份新V26 CSV也逐行确认均为0；本轮API使用各实际block尺寸及该值查询，目标核确实能升至12或16 warp。静态Shared表也正确。但这只回答“硬件允许放多少CTA”，不回答“本次Grid有多少CTA可放”。48个SM下：

- **ViT contract/qkv/expand：720p每次96 CTA，原2 CTA/SM容量恰好96；改3 CTA/SM容量144，独立同质Grid的理想容量波次仍1→1。** 1080p160 CTA，容量96→144，仍2→2；尾部规模会改变，但不是凭空多50%并行。
- **final_head：720/1080仅24/48 CTA**，原1 CTA/SM容量48已覆盖整Grid；设cap128把容量增至96，不会让24或48个CTA变成更多工作。
- **proj：36/80 CTA**，cap128后独立Grid理想波次720为1→1，1080为2→1，有后者的潜力。
- **proj_pool和几种128线程ffwd：36/80 CTA**，原2 CTA/SM容量96已覆盖两档完整Grid，3 CTA/SM不减少理想容量波次。

这是独立同质Grid的容量计算，**不是实际chained并发、跨核等待或SM分配的模拟**。chained核可以与前后核重叠，CTA分布不一定均匀，所以不能由“1→1”断言必无收益；反过来也不能由最大驻留+50%推导实际并行+50%。报告应把Grid规模与寄存器台阶一起列出。

## 5. 新编译实证：“只差8个REG”也可突然溢出136B

本轮V2.7基线上单核/分层改cap，O4原槽位均可容纳。不是假设，资源实测如下：

|目标|cap|实际REG|STACK B|API warp/SM|
|---|---:|---:|---:|---:|
|ViT contract|168|166|0|8→12|
|ViT qkv|168|168|64|8→12|
|expand publish / chained|168|168 / 168|168 / 160|8→12|
|final_head|128|128|136|8→16|
|proj_512|128|128|128|8→16|
|proj_pool|168|164|0|8→12|
|ffwd_proj / ffwd_proj_inpview|168|168 / 168|208 / 208|8→12|
|ffwd_inpview|168|168|120|8→12|
|C32 upsample|168|168|56|8→12|

STACK是资源报告字节数，不能直接当每帧显存流量；静态LDL/STL计数见 [resources.md](../ptx-patcher/v28/resources.md)，执行频率还受循环和分支影响。contract/pool是零spill候选，其余必须用整帧收益支付spill代价。`.maxnreg` 是上限，实际REG可低于168（166/164就是例子），不能把“少11个”当编译后精确变化。

第三节总述“差8～36”漏掉ffwd_inpview和upsample的44；前文“寄存器数完全相同”也应改“接近”（197落在196～200范围不等于四个数都相同）。FB03仅在标题出现，没有核名/cap实验定义，当前具体任务不含它；删去悬空标题或另列明确候选即可。HMMA2048/1536可追溯到V25插桩的循环执行计数，建议补该来源，不称为本轮V27硬件计数。

API口径依据：NVIDIA 的 [Occupancy API说明](https://developer.nvidia.com/blog/cuda-pro-tip-occupancy-api-simplifies-launch-configuration)将该计算称为理论最大occupancy；[CUDA Programming Guide](https://docs.nvidia.com/cuda/archive/12.6.1/cuda-c-programming-guide/index.html)将寄存器限制描述为每线程分配上限。本文具体数值以本机API和cubin为准。


## 6. 实测裁决：方向值得验证，但本轮不升级默认

十个单核/分层控制三档正反共240次正式运行，再用pool＋proj＋up组合做24次同规格确认；另11次快验。275次末帧全部相对V2.7严格0bit、无NaN/Inf，但没有一个方案满足三档双向净提速。contract零spill却在720p慢0.882%；pool在900/1080快0.228%/0.431%，720慢0.200%；up在1080快0.603%，900慢0.268%。组合720慢0.175%，900快0.360%，1080仅快0.037%。因此保留V2.7，不能把“硬件驻留跃迁靶点成立”写成“已找到可兑现收益”。完整每轮数值见v28结果表。
