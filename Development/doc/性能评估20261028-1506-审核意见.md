# 1506性能报告审核意见

**结论：实验数值和记录方式明显进步，可以支持“优先探索decode”；不能支持“pack已榨干、decode是唯一剩余缺口”。第三节两个优化方向有价值，但按当前文字直接实现，存在覆盖旧源值和跳过量化舍入的正确性风险。**

本次核对完整报告、配套JSON、两份探针/跑分脚本、v26生成器及V29既有实验。未重跑GPU，未检查本机五处部署；不改原稿、不stage、不commit。输入SHA、逐档重算及逐pass数据见[核验JSON](性能评估20261028-1506-审核核验.json)。

## 1. 数据通过，但“唯一decode”被本表直接反驳

60条未插桩记录、30条NVAPI记录数量正确。未插桩60条nonfinite均0；NVAPI记录均20帧、每帧82次、未知FB为0。五版各38活跃核的逐核SASS求和与TOTAL一致。新脚本补了DLL哈希、时间、summary和帧数校验，这些改进有效。

复算V29上的独立去pack：

|档位|V29−P0|占V29时间|方向|
|---|---:|---:|---|
|720p|0.344250ms|5.825%|4/4正|
|900p|0.297500ms|3.429%|4/4正|
|1080p|0.387000ms|3.283%|4/4正|

这不是零敏感度，也不是缺少全档一致性。报告一方面在表2.3标明12/12为正，一方面称decode“唯一具备全档一致显著正敏感度”，逻辑矛盾。没有方差检验时，建议用“方向一致、幅度较大”，不要把“显著”暗指统计显著性。

去decode的0.648250/1.105500/1.732250ms，以及去decode后再去pack的−0.080000/−0.309250/−0.780250ms复算正确。它们说明交互很强，不能用P1条件下的pack负效应否定原V29条件下的pack正效应——上一轮已经用数据纠正过这个推论，这轮不要又绕回来。

建议两项硬判断改为：**“当前已实现的fast pack稳定兑现约2%～3%整帧收益；仍存在破坏性去pack敏感度。decode敏感度更大，作为下一轮优先级，不排除继续改进pack。”**

## 2. 不能只取1080p NVAPI最小差值代表pack余量

1080p NVAPI V29−P0为0.173850ms，与同轮未插桩的0.387000ms差距明显；900p NVAPI则为0.544947ms，大于未插桩0.297500ms。两个计时域不要择小值当“已榨干”的证明。

FB05到P0的差值三档分别0.122803/0.143001/0.026394ms；仅突出1080p26.4μs，会遮住低分辨率仍有明显敏感度。900p本轮NVAPI V27→V29还反而慢0.075033ms，专门ABBA与长序列插桩结果并非完全同向。主性能判断优先专门未插桩ABBA合理，但模块归因需如实保留这些差异。

九条核心SASS是当前编译器、当前表达式的实测实现，不是指令下界证明。不同融合、布局、消费者、常量装载和调度都可能改变结果。FB01 STACK96→104B是事实；“因为提前调度源寄存器读取”需要具体live-range/调度对照，目前仅能列为假设。

## 3. Pool Cap方向值得试，但必须把源快照和瞬时工作集算进去

`v26/codegen.py` 不总是在run开头解码。它用 `when=min(first_use,first_write//2)`，通常按需解码，**在源被d0/d1提前覆写时主动提前解码以保存旧值**。不能把这部分保活简单视作冗余缓存。

若驱逐decoded pair后再次从r解码，而r已经被此前MMA写坏，就会读到新累加值，产生功能错误。实现必须满足至少一项：源在最后一次重解码前不被写；或在首次覆写前保存原encoded b32快照，并把快照寄存器和生命周期计入预算。保存了一个b32不等于无成本，也可能抵消收益。

“一对scratch即用即解”也不能覆盖一个完整MMA站点：单条m16n8k16需要A四个、B两个操作数同时存在，最坏六个独立非mapped half2。一个scratch不能在依次解码后只留下最后一个值就执行MMA。要明确缓存上限、当前指令必需临时槽位和备份槽位，预算不能低于当前工作集。

释放PTX虚拟寄存器名并不保证物理REG或STACK按比例下降；延长encoded源活跃期和增加decode指令可能反向增加压力，必须看ptxas/API及同轮计时。

还有一条重要反证：**本报告自己列出FB04在P1去decode后仍为88B STACK**（V29也是88B）。所以“临时池直接导致FB04的88B，封顶即可清零”没有证据。FB01降104→32B也不是归零。应写“测试是否减spill”，不要预设清零。

## 4. Phase-Split不是无条件把总峰值减半

对无别名、仅使用一次的encoded源，低相解码→MMA→高相解码确实有机会让该源decoded存储从2降为1，但第一条K16可能覆写第二相仍要读取的encoded源，必须在第一相写前备份。C累加器、mapped备份、其他仍活跃decoded缓存也不随之减半。

建议先限定“单次使用、两相之间源不被写”的安全子集；保留现有d0/d1别名用例，另加同一K32第一相覆写高相源的测试，再逐步扩展。不要声称整个核临时峰值直接减半。

## 5. mapped放宽：唯一到达定义只是必要条件，不是充分条件

需要证明的是**所有到达路径的当前定义唯一**，不是“另一处定义不支配该点”。非支配定义仍可能沿某一分支到达；循环回边会让文本上的后续定义到达下一迭代。还要检查谓词写、low/high源重定义、half-pair组合、跨run备份及路径上的消费者。

更重要：`half2 -> FP8 -> half2`包含量化，原始half2通常不等于解码后的FP8。mapped直通原生half2会跳过舍入/饱和；到达定义完全正确也不能证明严格0bit。旧multidef_nq本身属于既定数值路线，不意味着新放宽的36项自动数值等价。

因此必须独立核验 **数据流安全** 和 **量化等价性/允许的质量变化**。另外36是静态run事件而非36个独立源码站点，要先按真实定义及消费者去重。上游pack是否能删还取决于有没有别的消费者，不能保证“放行即同时删pack”。

## 6. 其他口径小修

- V29的96次正式运行包含A Exact与B Fast；其中V27对Fast的专门对照是48次。12方向Fast皆正和两轮合并均值成立，标题不要把96都说成Fast对照。99次还含3次快验。
- 65,496/65,536的全值结论与V29交叉通道测试相容，但建议另附单通道40个反例列表及字节距离检查。“差1 ULP”应明确是E4M3量化码点，不是half ULP；不表示整网只改40处。
- 相对multidef_nq更近不是更接近原生GPU或F32真值。该参考的PSNR应补输入、SHA和质量比较原始记录；本轮60条性能raw不承载这项画质证明。“V1完整O4”也要避免与历史safe/O1 V1混称。
- sampled `sw_thermal_slowdown=0`不等于全过程没有任何降频。394个离散活跃样本未覆盖所有瞬时状态；功耗限制、硬件thermal reason、GPU boost等仍可能改变频率。“全程低于温度墙”改成“采样最高84°C，所监控的软件温控标志未激活”；86°C阈值若无设备查询出处，不要当通用硬值。
- 独立探针仍破坏数值语义。nonfinite=0只说明输出有限，不证明输入分布、分支、缓存路径与原计算相同。敏感度不是保证可回收预算。

## 建议裁决

**保留V29_fast已验证的提速与非0bit质量说明；先做一项受限的decode重算/半相实验，别同时放宽mapped。** 用原源快照和当前指令工作集约束保证正确性，然后观察实际STACK/REG，而不是先按PTX临时名估计收益。

工程优先级可以选decode，但应删掉“pack无需再投”“九条已无可合并”“唯一剩余缺口”“池封顶消除spill”等越过证据的定论。本版主要问题是结论和下一刀的正确性条件，不是主体跑分数字。
