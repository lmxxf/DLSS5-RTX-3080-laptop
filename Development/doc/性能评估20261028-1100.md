## 一、 核心结论直答：还有没有算力缺口？缺口在哪？

**硬结论**：
1. **在“不改动二进制模型权重与网络拓扑、仅在原版 PTX 上做 `sm_86` 重编译改写”的边界内，`PTX V2.7` 已经逼近该路线的工程极限**。
2. 为了精确测定“当前 `PTX V2.7` 的整帧耗时（`5.92 / 8.67 / 11.38 ms`）里到底还有多少软件仿真开销、多少架构代差、多少内存与同步硬底子”，我们直接构造了 **3 个硬件消融探针 DLL（`P1_ZeroDecode`、`P2_ZeroPack`、`P3_1xHMMA`）** 上机实测，将整帧 GPU 耗时精确切分为三大物理板块：

| 物理耗时板块 | 测定方法（硬件消融探针差值） | 720p (1280×720) | 900p (1600×900) | 1080p (1920×1080) | 占整帧比例 | 物理本质与可优化性判定 |
|:---|:---|---:|---:|---:|---:|:---|
| **① 剩余软件仿真开销**<br>（非 `mapped` FP8→FP16 解码 + 解码临时寄存器池压力） | **`V2.7 − P1_ZeroDecode`**<br>（100% 删去剩余非 `mapped` 8 指令解码与 20~112 临时寄存器池） | **`0.619 ms`** | **`1.049 ms`** | **`1.460 ms`** | **`10.5% ~ 12.8%`** | **这是全网仅剩的软件转译开销**。其中 `70%~80%` 来自 `ld.global` 预打包 FP8 模型权重在进入 FP16 Tensor Core 前的必经寄存器解包；除非把权重离线膨胀为 FP16（显存带宽翻倍得不偿失），否则在核内已压至 8 条 ALU 指令下界。 |

| **③ 原生单拍计算 + 访存与同步固有底座**<br>（单拍 `1×HMMA` + `LDG/STG/LDS/STS` + `bar.sync` + 非 MMA 算子） | **`P3_1xHMMA` 实测值**<br>（0 解码 + 0 打包 + 单拍 `1×HMMA` 硬件执行时间） | **`3.693 ms`**<br>*(含单拍 MMA `~1.61ms` + 访存/同步底座 `~2.08ms`)* | **`5.345 ms`**<br>*(含单拍 MMA `~2.27ms` + 访存/同步底座 `~3.07ms`)* | **`7.183 ms`**<br>*(含单拍 MMA `~2.73ms` + 访存/同步底座 `~4.45ms`)* | **`61.7% ~ 63.1%`** | **31 块神经网络本身的固有计算与带宽底座**。即使在一块拥有原生单指令 K32 吞吐且 0 解码开销的理想 `sm_86` GPU 上，跑完这 82 次发射也至少需要 **`3.69 / 5.35 / 7.18 ms`**。 |

## 四、 剩余算力缺口的四大物理根因与可优化性终审

通过上述消融探针与硬件 Roofline 数据，我们可以对 `PTX V2.7` 剩余的每一处性能缺口给出定性+定量的终审判断：

### 1. 为什么 `SWAR` 量化打包（11.6 万条静态 SASS）已经完全不是瓶颈？
- **实验证据**：从 `P1_ZeroDecode` 到 `P2_ZeroPack`，我们将全网所有写入 Shared / Global Memory 的 15 指令 `FP16x2→FP8x2` SWAR 打包替换为单条 `cvt.u16.u32`，静态 SASS 指令从 `379,890` 条暴减 `116,100` 条至 `263,790` 条（`-30.6%`）。然而在未插桩实测中，720p 仅快 `0.023 ms`（`0.4%`），900p 和 1080p 反而因为写回脉冲提前加剧了 L2/Shared 端口争用而微慢 `0.17 ~ 0.36 ms`。
- **物理机制**：在 `V2.1 / V2.6` 消除了寄存器内 `mapped` 激活值的量化打包后，残存的 `FP16→FP8` 打包 **只存在于内层 K 循环之外的 Tile 输出写回阶段（Epilogue）**，执行频次比内层 MMA 解码低一个数量级，且完全隐藏在 `STS / STG` 写回延迟之下。因此 **继续压缩 `FP16→FP8` 打包指令的收益为 0**。

### 2. 剩余的 `0.60 ~ 1.47 ms`（`10.1% ~ 13.0%`）非 `mapped` 解码与寄存器池开销，为什么在纯 PTX 层已触底？
- **来源构成**：经 `V2.7` 完整 CFG 定义可达性（may-reaching definitions）审计，全网活跃核中剩余的非 `mapped` 解码事件（`FB00` 844 个、`FB01~03` 各 1052~1244 个、`FB04` 864 个、`FB05` 512 个）由两部分组成：
  1. **全局内存预打包数据（占 `50% ~ 77%`，如 `FB00` 中占 `76.8%`、`FB01` 占 `68.4%`）**：主要是模型預训练好的 FP8 权重（通过 `ld.global` 或 `cp.async` 载入）。只要不改动 DLL 外部/内部的二进制权重存储格式，权重进入 `sm_86` 的 FP16 Tensor Core 前就必须在寄存器内将 1 个 `.b32`（4×FP8）拆解为 2 个 `.b32`（2×FP16x2）。`V2.6` 的 `prmt + and + shl + hmul2`（每半字 4 条、每对 8 条指令）已是无硬件 FP8 转换器条件下的最少指令数。
  2. **跨线程 Shared Memory 交换特征（占 `23% ~ 50%`，如 `FB02/03` 中占 `53%~60%`、`FB05` 占 `50%`）**：上游算出的激活值先量化为 FP8 存入 `shared_storage`（或由 `cp.async` 从全局内存直接拷入 `shared_storage`），经 `bar.sync` 后由不同线程按矩阵分块重新读取（`ld.shared`）。由于跨过了 `bar.sync` 且读写线程索引映射不同（加上 `FB02~05` 的 `shared_storage` 混有 `cp.async` 全局源），无法在不重写整核 Shared Memory 布局与容量（翻倍 Shared Memory 会直接砍半 CTA 驻留）的前提下做寄存器级 FP16 旁路。
- **寄存器池与 Spill 权衡**：在 `FB01 (C64)` 中，28 对非 `mapped` 解码临时寄存器（56 个 `.b32`）在 `.maxnreg 168`（`12 Warps/SM`）下带来 `104 B STACK`（在 `P1` 中消除该池可省 `0.077 ~ 0.172 ms`）。但在 `V2.7` 中已实测：若将 `FB01` 放宽至 `.maxnreg 192` 来把 `STACK` 压到 `48 B`，其驻留会因硬件分配粒度从 `6 CTA (12 Warps/SM)` 跌至 `4 CTA (8 Warps/SM)`，整帧反而变慢 `0.38% ~ 0.47%`。因此当前的“保留 `12 Warps/SM` + 容忍少量 L1 命中的局部 spill”已是实测最优平衡点。

### 3. 为什么 `FB05 (ViT)` 与 `FB04 (C512)` 压低 `.maxnreg` 提高理论驻留上限无法提速？
- **实验证据**：`V2.8` 对 `FB05` 与 `FB04` 进行了 10 项单核与分层 `.maxnreg` 控制实验（275 次运行），哪怕是 **`0 B STACK` 零栈溢出** 的 `vit_contract`（`cap168` 驻留 `2 → 3 CTA/SM`）和 `proj_pool_512`（`cap168` 驻留 `2 → 3 CTA/SM`），在 720p 下也分别变慢 `-0.882%` 和 `-0.200%`。
- **物理机制（有限小 Grid 波次边界）**：
  - 在 720p 下，`FB05 (ViT)` 的每次发射整个 Grid 只有 **`96 CTA`**！在默认 `.maxnreg 255` 下，单 SM 驻留为 `2 CTA/SM`（`8 Warps/SM`），全卡 48 个 SM **第一波（`48 SM × 2 CTA/SM = 96 CTA`）就已经把整个 Grid 100% 装满并并发执行了**！
  - 在整张卡连第 97 个 CTA 都没有的情况下，强行把单 SM 容量上限从 `2 CTA/SM` 提高到 `3 CTA/SM`（容量 `144 CTA`），**实际活跃 Warp 数仍然是 96 个 CTA（0 增益）**，反而因为人为缩小了每个线程可用的物理寄存器窗口，迫使 `ptxas` 缩短预取距离（ILP 下降），导致零 spill 核也变慢！
  - 同理，`FB04 (C512)` 的 `final_head` 在 720p/1080p 仅 `24 / 48 CTA`（`1 CTA/SM × 48 SM` 一波装完），`pool` 与 `ffwd` 在 720p 仅 `36 CTA`（不足 48 SM，连 `1 CTA/SM` 都装不满）。只有拥有 **数千至上万个 CTA** 的 `FB00 (C32)` 才能真正吃满 `8 → 12 Warps/SM` 的驻留红利（即 `V2.7` 已兑现的收益）。

### 4. `FB05 (ViT)` 与 `FB00 (C32)` 各自的真实物理瓶颈是什么？
- **`FB00 (C32)`（占整帧 `28.6% ~ 34.0%`）**：**高度算力受限（Compute / Tensor Core Bound）**。其 `TC_SOL%` 已高达 **`72.8% ~ 75.8%`**（剥离剩余权重解码后达 **`80.5% ~ 84.0%`**），4 个主力核已跑在 `12 Warps/SM`（硬件 `16 CTA/SM` 上限下的最高免大溢出一档）。
- **`FB05 (ViT)`（42 次发射，占整帧 `27.3% ~ 33.6%`）**：**受限于“小 Grid 波次粒度的尾效应 + 42 次链式（`chained`）跨层同步与 `LDGSTS` 异步访存延迟”**。其 `TC_SOL%` 在 720p 为 `52.0%`（96 CTA 恰好 1 波，但各块循环 15~16 圈的 `bar.sync` 与 `mbarrier` 同步等待占了约 40% 时间），在 1080p（`160 CTA`，按 `2 CTA/SM × 48 = 96 CTA/波` 需跑 `1.67` 波，第 2 波只装满 `64/96 = 66.7%` 的 SM 槽位）升至 `57.7%`。

## 五、 总结

1. **当前状态**：`PTX V2.7` 在保持与 `V2.6` 严格 `0 bit-diff`（对 `V1` PSNR `62.12 / 61.85 / 60.88 dB`，天空 `0` 变号）的前提下，将 RTX 3080 Laptop (`sm_86`) 上的 DLSS 5 帧耗时推至 **720p `~5.92 ms` / 900p `~8.67 ms` / 1080p `~11.38 ms`**（较 `v0.2.0` 净降 **`11.7% ~ 12.8%`**，吞吐提升 **`+13.3% ~ +14.7%`**）。
2. **算力缺口终判**：通过三阶硬件消融探针实测，整帧耗时中 **`61.7% ~ 63.1%`** 是网络固有的单拍计算与访存/同步底座，**`24.0% ~ 27.2%`** 是 Ampere 缺少原生 K32 Tensor Core 导致的第 2 拍 `HMMA.16816` 硬件代差，**仅剩 `10.5% ~ 12.8%`（`0.62 ~ 1.46 ms`）属于非 `mapped`（权重与跨线程共享内存）的 FP8→FP16 解码与临时池开销**。在纯 PTX 重编译范畴内，`PTX V2.7` 已无值得冒画质或寄存器溢出风险去抠的余量，可直接作为最终生产版本打包发布。
