## 一、吸收 `0207` 审核意见后的核心事实校准与 `PTX V2.7` 成果

在上一轮（`20261028-0207`）评估审核中，通过本机 CUDA Occupancy API 查询 `V2.6` 实际 cubin 与完整 CFG 数据流审计，纠正了此前用粗略总寄存器除法估算驻留的偏差，并据此完成了 **`PTX V2.7`**：

1. **`FB00 (C32)` 六个活跃核的真实寄存器与 CUDA Occupancy API 理论驻留上限**：
   - 在 `V2.6` 中，6 个活跃 C32 核（均为 32 线程 = 1 Warp/CTA，`pre_block` 静态 Shared `2,048 B`、其余 `0 B`）的物理寄存器分别为：`pre_block` `196`、`outview_wait` `197`、`ds_wait` `199`、`inpview_tilesync` `200`、`upsample_tilesync` `212`、`post_block` `242`（此前报告写 `196~212` 漏计了未下降的 `post_block` `242`）。

### 2. `FB01 ~ FB05` 非 `mapped` 操作数来源审计结论
通过完整 CFG `may-reaching definitions` 审计（并修复了旧定义解析器漏识别带 `::` 限定符如 `ld.shared::cta` 的工具缺陷，验证 112 个入口 `mapped` 映射不变，详见 [v27/source-results.md](../ptx-patcher/v27/source-results.md)）：
- `FB01 ~ FB05` 的非 `mapped` 静态 run 事件主要由 **全局加载根（`global_load`，参数偏移 `param64+16` 或 `+24`）** 与 **共享内存加载根（`shared_load`）** 构成，并非同基本块内单纯的 `mov.b32 {rs0, rs1}` 被误拒（`FB01~03` 无直接 `pack_multidef` 拒绝，仅 `FB00` 有 `32` 项、`FB05` 有 `4` 项及 `16` 项控制流合流）；
- 达到各 FB 临时池峰值（`56 / 56 / 56 / 112 / 80` 个 `.b32`）的活跃 run 首峰值组成为：`FB01/02/03` 各 `24 global + 4 shared` 对，`FB04` 为 `48 global + 8 shared` 对，`FB05` 为 `32 global + 8 shared` 对；
- 虽然 `FB01` 等模块的 `shared_storage` 写源来自本地 FP8 量化，但因涉及跨线程/跨 Warp 交换、同步及量化截断语义，不能简单通过放宽 `mapped` 规则免费消除。

## 三、`V2.7` 之后的新发现：将 Per-Kernel 精准 `.maxnreg` 驻留跃迁扩展至 `FB04 / FB05`（`PTX V2.8` 待验证靶点）

`V2.7` 证明了一个极其重要的方法论突破：**同一个 Fatbin 内部的不同 Kernel 具有截然不同的寄存器需求；过去按整个 Fatbin 一刀切设置 `.maxnreg`（例如把整个 `FB04` 或整个 `FB05` 设为 `168`），会因为其中某 1 个 255 寄存器的重型核（如 `FB04` 的 `qkv_512`、或 `FB05` 的 `attention_chained`）发生严重 spill 而掩盖了同 Fatbin 内其他轻型核跨越驻留台阶的正收益！**

审查 [v27/occupancy-baseline.json](../ptx-patcher/v27/occupancy-baseline.json) 中 `V2.6` 全部 40 个活跃核的真实寄存器数、Shared Memory 与当前理论驻留，发现 **`FB05 (ViT)`、`FB04 (C512)`、`FB03 (C256)` 与 `FB00 (C32)` 中还存在一批“仅高出硬件驻留台阶边界 `8 ~ 36` 个寄存器、且 `STACK = 0 B`、Shared Memory 充裕”的独立活跃核**，在 `V2.7` 中尚未被单独调优：

### 靶点 1：`FB05 (ViT)` 中 4 个非 `attention` 主力计算核的独立 `.maxnreg 168` 跃迁（`8 → 12 Warps/SM`）
在 `FB05` 中，此前整包压 `168` 之所以失败（慢 `4.2%`），是因为 `cc_vit_1d_attention_chained_fp8` 用满了 `255` 个寄存器（压 `168` 会产生 `176 B` spill）；但看其余 4 个占了 ViT 绝大部分耗时的 128 线程（4 Warps/CTA）主力核：
1. **`cc_vit_1d_ffn_contract_chained_fp8`**（每帧发射 **8 次**，每 Warp `2,048` HMMA）：当前 **`REG = 179`**，`STACK = 0 B`，`SHARED = 16,400 B`（3 CTA 仅需 `49,200 B <= 102,400 B`），当前理论驻留仅 **`2 CTA = 8 Warps/SM`**！**距离 `.maxnreg 168` 台阶（跃升至 `3 CTA = 12 Warps/SM`，+50% 驻留）仅差 `11` 个寄存器！**
2. **`cc_vit_1d_qkv_chained_fp8`**（每帧发射 **8 次**，每 Warp `1,536` HMMA）：当前 **`REG = 197`**，`STACK = 0 B`，`SHARED = 8,208 B`（与 `FB00` 中成功跃迁的 4 个 C32 核寄存器数 `196~200` 完全相同！），设 `.maxnreg 168` 即可从 **`8 Warps/SM` 升至 `12 Warps/SM`**！
3. **`cc_vit_1d_ffn_expand_publish_fp8` (`REG = 202`)** 与 **`cc_vit_1d_ffn_expand_chained_fp8` (`REG = 204`)**（共发射 **8 次**，每 Warp `2,048` HMMA）：`STACK = 0 B`，`SHARED = 24,600 B`（3 CTA 需 `73,800 B <= 102,400 B`），设 `.maxnreg 168` 同样可从 **`8 Warps/SM` 升至 `12 Warps/SM`**！
- **待验证方案**：保持 `cc_vit_1d_attention_chained_fp8` (`255` regs) 与 `projection` (`145` regs，已达 `12 Warps/SM`) 不动，单独测试将 `contract (179)`、`qkv (197)`、`expand (202/204)` 分级设为 `.maxnreg 168` 的理论驻留、spill 字节数与整帧耗时收益！

### 靶点 2：`FB04 (C512)` 中轻/中型核的独立 `.maxnreg 128 / 168` 跃迁（`8 → 16` 或 `8 → 12 Warps/SM`）
在 `FB04` 中，此前整包压 `168` 之所以产生 `640 B` spill，完全是因为 `cc_split_swin_16h_qkv_512_chained_fp8` 用满了 `255` 个寄存器（且已有 `88 B` spill）；而看其余核：
1. **两个 256 线程（8 Warps/CTA）的轻型核，距 `.maxnreg 128` 台阶（从 `1 CTA = 8 Warps/SM` 翻倍至 `2 CTA = 16 Warps/SM`！）仅差 `8 ~ 13` 个寄存器**：
   - **`cc_split_swin_16h_final_head_512_wait_fp8`**：`threads = 256`，`SHARED = 12,312 B`，`STACK = 0 B`，**`REG = 136`**（距 `128` 仅差 **`8` 个寄存器**）！
   - **`cc_split_swin_16h_proj_512_chained_fp8`**：`threads = 256`，`SHARED = 12,312 B`，`STACK = 0 B`，**`REG = 141`**（距 `128` 仅差 **`13` 个寄存器**）！
2. **四个 128 线程（4 Warps/CTA）的中型核，距 `.maxnreg 168` 台阶（从 `2 CTA = 8 Warps/SM` 升至 `3 CTA = 12 Warps/SM`）仅差 `12 ~ 44` 个寄存器**：
   - **`cc_split_swin_16h_proj_pool_512_chained_fp8`**：`threads = 128`，`SHARED = 8,208 B`，`STACK = 0 B`，**`REG = 180`**（距 `168` 仅差 **`12` 个寄存器**）！
   - **`cc_split_swin_16h_ffwd_proj_512_chained_fp8` (`REG = 204`)**、**`ffwd_proj_inpview` (`REG = 205`)**、**`ffwd_inpview_512_tilesync` (`REG = 212`)**：`threads = 128`，`SHARED = 8,208 ~ 12,312 B`，`STACK = 0 B`。
- **待验证方案**：保持 `qkv_512` (`255` regs) 与 `ffwd_512` (`174` regs, 256 threads) 不动，测试上述轻/中型核单独跨越 `128 / 168` 驻留台阶的收益。

### 靶点 3：`FB00` 第 5 核 `upsample_tilesync` (`REG = 212 → 168`) 与 `FB03 (C256)` 核级探索
- 在 `V2.7` 已选的 `FB00` 四核 `168` 基础上，单独测试第 5 核 `cc_tinlayout_fused_swin_1h_32_1_upsample_tilesync_fp8` (`REG = 212`, `STACK = 0`, `SHARED = 0`) 设为 `.maxnreg 168`（升至 `12 Warps/SM`）时的 `STACK` 与整帧耗时变化。
