# 《性能评估20261028-0207》审核意见

**结论：第一节的性能、精度和大部分SASS数据可以保留；第二节把假设标为待验证，比上一版严谨。但C32驻留表存在实错，非mapped来源的二分法也不完整。** 本次已结合V2.6实际cubin、CUDA Occupancy API、CFG数据流和新NVAPI捕获核验，并据此选择V2.7实验。

对象为commit `f704353` 的[原稿](性能评估20261028-0207.md)，SHA256 `72f865c754a42fbc0c0b39ba4bdfd8022a6b016040acbed14c65cf5911e2b7eb`。原稿不修改；审核与核验JSON随本轮工程提交。行号指原稿当前版本。

## 1. 必改：第53～59行总寄存器除法不是可实现的驻留数

本机API返回：48SM、每SM 65,536个32位寄存器、最大1,536线程/48warps、最大16CTA、Shared上限102,400B。直接加载V2.6 cubin，以真实32线程CTA查询，六个活跃C32核目前**全是8 CTA/SM＝8 warps/SM**。

针对文中四个核（prefix、inpview、ds_wait、outview）实际编译不同cap后，查询结果如下：

| 配置 | 实际REG范围 | 每SM最大CTA/warps | 四核STACK（prefix/inpview/ds/outview） |
|---|---:|---:|---|
| V2.6原配置 | 196～200 | **8 / 8** | 0 / 0 / 0 / 0B |
| cap192 | 191～192 | **8 / 8** | 0 / 0 / 0 / 0B |
| cap184 | 184 | **8 / 8** | 0 / 0 / 0 / 0B |
| cap168 | 168 | **12 / 12** | 0 / 8 / 8 / 16B |

所以200/192对应10、184对应11的结论不成立。`floor(65536 / warp寄存器数)`是粗略总量上界，未完整反映资源分配/分区约束；不能用它替代Occupancy API。

**Shared与CTA限制也应分别说明**：prefix静态Shared为2048B，其余C32为0；它们在8/12 CTA处不受Shared总量限制，当前16 CTA硬上限也尚未绑定。但只要保持一warp/CTA，即使寄存器继续减少，16 CTA上限也使其最多16 warps/SM，不能一路套总寄存器除法推到48。

这是CUDA API在该函数配置下的**理论驻留上限**，不是D3D12动态活跃warp计数。真正值得测试的是168台阶与新增spill的权衡；192/184仍可能改变代码调度，但不能以“增加驻留”解释它们的收益。

证据：[baseline API](../ptx-patcher/v27/occupancy-baseline.json)、[cap API](../ptx-patcher/v27/occupancy-caps.json)、[逐核构建范围](../ptx-patcher/v27/caps.json)。本轮只调上述四核，未把post/upsample一起强压168。

## 2. 必改：第36、50行的“活跃C32寄存器范围”漏了post_block

全六个活跃C32核是 **229～242 → 196～242 regs**。post_block仍为242；229～236→196～212只适用于那五个发生下降的核。第55行明确限定的四核196～200则正确。

建议将表行标题改为“五个寄存器数下降的C32核”，或采用完整范围并把post单列。post仍高寄存器且有可观耗时，是后续不应遗漏的独立对象；其他核减少寄存器，不能自动归因到它。

## 3. C64从168微调到176也会跨越驻留台阶

新基线确实值得重测，但“只加8个寄存器”不等于低代价。V2.6的四个活跃C64核在168下是6 CTA/12 warps；176、184、192都变为4 CTA/8 warps。

| C64 cap | 活跃四核最大STACK | 理论warps/SM |
|---|---:|---:|
| V2.6原168 | 96B | 12 |
| 176 | 72B | 8 |
| 184 | 56B | 8 |
| 192 | 48B | 8 |

全导出104B与活跃96B是不同范围，原稿已有区分，应保留。可以提出新权衡假设，但必须同时计算驻留损失，不能从spill减少单独预言加速。cap192已纳入本轮三档配对，结果见[V2.7实验表](../ptx-patcher/v27/results.md)。

## 4. 非mapped不等于“被过严的跨块规则拒绝”，Shared也不等于“真外部权重”

`build_sm86_dlls.py`默认使用 `multidef`，即 `local_only=False`，现有过滤器的跨基本块限制在此模式已经关闭。它仍检查多定义、转换次序等，并用文本位置限制使用；**它不是完整CFG支配证明器**。因此第72行“作用域/支配规则”的表达应收窄。

本轮用完整opcode解析、CFG may-reaching definitions和寄存器拷贝追溯审计了所有活跃FB00～06。计数单位是**每个静态MMA run内唯一的编码操作数**（实际只解包一次），不是每条MMA重复使用次数，也不是动态帧频率。

| FB | 非mapped静态run事件 | global根或其phi（含少量零填） | shared根 | global/本地FP8量化混合根 |
|---|---:|---:|---:|---:|
| 01 | 1052 | 724 | 328 | 0 |
| 02 | 1244 | 588 | 656 | 0 |
| 03 | 1188 | 476 | 712 | 0 |
| 04 | 864 | 512 | 352 | 0 |
| 05 | 512 | 240 | 256 | 16 |

**这不是一大批单纯函数内pack被误拒绝。** FB01～03没有这种直接拒绝案例；FB05的16项是不同控制路径合流，并非始终由同一个half对产生。直接`pack_multidef`拒绝的静态run事件为FB00 32、FB05 4，追溯拷贝后会覆盖更多别名，不能只按原寄存器名数一次。

更重要的是，Shared加载的数据还可能是**本函数先量化再写入的中间特征**：C64的`shared_storage`写入来源是本地FP8量化；C128/C256及FB04/05一些共享缓冲同时可能接收加载/异步拷贝与本地量化结果。因此第73行把`ld.shared/ld.global`统称“真外部FP8数据”不准确。global也只按参数地址根分组，未无证据地一律认定为权重。

这指出了一个真实待研究的问题：局部量化→共享存储→再解包的往返及跨warp重排。**但它不能靠放宽mapped规则免费消除**：要证明数据版本、线程布局、同步与FP8量化语义。直接拿量化前half替代pack/unpack后的值，会改变当前数值函数。共享FP16布局或重算/缓存取舍是新的实验设计，尚未因本次来源审计而得到性能保证。

所有FB01～05的最大临时池在活跃核里确实仍可出现，不只是未执行变体的最大值。最高池run的首次峰值live set仍主要由global/shared编码源构成；没有发现同基本块内可直接合并的纯mov别名重复解包。详见[来源摘要](../ptx-patcher/v27/source-summary.json)、[完整逐事件定义证据](../ptx-patcher/v27/source-audit.json)。

## 5. 本轮新发现：定义解析器漏认带`::`限定符的指令

旧`ptx_mapped.instructions`的opcode正则不包含冒号，会漏掉`ld.shared::cta`、`ld.global.L1::no_allocate`一类定义。本次审计必须补齐解析，否则会把大量shared加载错误统计为“未定义”。

这是工具/防御性正确性问题，**不是本轮已发现的画面故障或新性能收益**：112个入口修复前后的mapped集合与值映射完全相同，修复后全15重建V2.6 DLL，SHA仍精确等于`04b01f0c...`。生产解析器已补齐并新增限定符多定义保护用例；没有借修复悄悄放宽当前mapped集合。

[映射对照](../ptx-patcher/v27/parser-scope-check.json)、[二进制复验](../ptx-patcher/v27/parser-binary-check.json)、[回归](../ptx-patcher/v27/regression.log)。

## 6. 高半字的bit31已对齐，只解决了其中一个符号位

第67行可以保留为问题，但必须同时列出byte2的约束。乘scale前，高半字目标可写为：

```text
((R & 0x007f0000) >> 9) | ((R & 0x00800000) >> 8)
| ((R & 0x7f000000) >> 1) | (R & 0x80000000)
```

byte2幅值要移至bit7..13、符号要从bit23移至15；byte3幅值要移至23..29，而符号才是原位bit31。不能仅由最后一项原位就认定PRMT冗余。

V2.5证实的是**该Hybrid整体改写**伴随SHF/LOP3增加并回退，不是对所有SHR方案的普遍否定，也未单独证明回退由SHR造成。应按具体序列的SASS、依赖与资源变化重新测试。
