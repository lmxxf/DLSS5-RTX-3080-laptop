## 一、 核心结论与当前性能发挥定性

### 1.1 `PTX V2.9_fast` 已兑现的收益与画质边界
1. **指令与静态代码缩减**：`PTX V2.9_fast` 采用 9 条核心 SASS 的 Unified Mul Pack（`mul.rn.f16x2 0x1c001c00` 统一 E4M3 Normal/Subnormal 指数对齐 + `lop3 0xd8` + `prmt 0x4431` 高字节拼符号，仅需 2 个 `.b32` 临时寄存器），替换了 `V2.2~V2.7` 使用的 13 条核心 SASS SWAR Pack（5 个 `.b32` 临时寄存器）。在 `FB00..FB06` 全部 **38 个实际发射活跃核** 中，非 NOP 静态 SASS 指令从 `175,685` 条降至 **`163,944` 条（净减 `11,741` 条，`-6.68%`）**；按含固定尾部 NOP 的 `v29/audit.py` 口径则从 `176,431` 条降至 **`164,659` 条（净减 `11,772` 条，`-6.67%`）**。
2. **双版本同轮配对提速（`v29/README.md` 96 次正式运行）**：在 `V2.7` 与 `V2.9_fast` 的两轮（`first` + `repeat`）三档分辨率正反 ABBA/BAAB 对照中，`V2.9_fast` 在 **全部 12 个正反方向上 100% 取得正收益**：
   - **第 1 轮（`first`）**：720p `6.02850 → 5.87400 ms`（**`-2.563%`**）、900p `8.83450 → 8.58125 ms`（**`-2.867%`**）、1080p `11.64550 → 11.28750 ms`（**`-3.074%`**）；
   - **第 2 轮（`repeat`）**：720p `6.05300 → 5.89575 ms`（**`-2.598%`**）、900p `8.90400 → 8.72575 ms`（**`-2.002%`**）、1080p `11.59850 → 11.39450 ms`（**`-1.759%`**）；
   - **两轮 8 进程合并均值**：720p **`6.04075 → 5.88488 ms (-2.580%)`**、900p **`8.86925 → 8.65350 ms (-2.433%)`**、1080p **`11.62200 → 11.34100 ms (-2.418%)`**。
3. **画质与数值边界**：在全部 65,536 个 `uint16` 位型中，`V2.9_fast` 有 `65,496` 个（`99.939%`）与 `V2.7` 逐位一致，仅 40 个深层 subnormal 边界码点差 1 ULP。整网相对 `V2.7` 的 PSNR 为 **`62.609 / 62.117 / 60.595 dB`**（`maxabs` `0.004395 / 0.005615 / 0.007446`）；相对 `V1` 完整 `O4` 参考（`multidef_nq.dll`）的 PSNR 为 **`61.91 / 60.27 / 61.45 dB`**（其中 720p 与 1080p 均略高于 `V2.7` 对 `multidef_nq.dll` 的 `61.42 / 60.51 dB`），99 次运行 `nonfinite = 0`，720p 天空测试 `变号 = 0`。

### 1.2 站在 `PTX V2.9_fast` 新基线上的两大硬判断（供审核与挑战）
本轮我们以 **`V2.9_fast`** 为新原点，构建了 `P0_ZeroPack`（将 pack 替换为单条 `cvt.u16.u32`）、`P1_V29_ZeroDecode`（保持 `V2.9_fast` 的 9-SASS pack，仅旁路 non-mapped 8 指令解码与 `vlh_t` 临时池）及 `P2_Both`（同时应用 `P0` 与 `P1`），連同旧基线 `V2.7` 进行了五版本正反序对照（60 次未插桩 + 30 次 NVAPI 捕获），得出以下两项明确判断：

1. **硬判断一：`FP16x2 → FP8x2` 打包（Pack）路径在 `V2.9_fast` 已基本榨干，无需继续在 Pack 指令条数上投入**。
   - **证据 ①（NVAPI 核内差距已大幅收窄）**：在 720p 与 1080p 的同轮 NVAPI 逐核捕获中，`V2.7 → V2.9_fast` 已分别兑现了 **`+0.218700 ms`**（`6.128870 → 5.910170 ms`）与 **`+0.490368 ms`**（`11.702912 → 11.212544 ms`）的核内节省；其中在之前对 Pack 最敏感的 **`FB05 (ViT)`** 上，1080p 耗时从 `3.266995 ms` 降至 `3.048730 ms`（省下 **`0.218265 ms`**），距离完全删除 Pack 算术的破坏性探针 `P0_ZeroPack`（`3.022336 ms`）仅差 **`0.026394 ms`（`26.4 μs`）**；`FB00 (C32)` 在 1080p 下距离 `P0` 也仅差 **`0.040371 ms`**（全网 82 核合计 `V2.9_fast − P0` 在 1080p NVAPI 下仅剩 **`0.173850 ms` / `1.55%`**）。
   - **证据 ②（去 Decode 条件下的纯负效应）**：当在 `P1_V29_ZeroDecode`（已移除 non-mapped 解码）的基础上，将 `V2.9_fast` 的 9-SASS Pack 替换为单条 `cvt.u16.u32`（即 `P1_V29 → P2_Both`）时，**三档分辨率全部 12 个未插桩 pass 与全部 6 个 NVAPI pass（18/18）一致变慢**：未插桩 `P1_V29 − P2` 为 **`-0.08000 ms`（720p）/ `-0.30925 ms`（900p）/ `-0.78025 ms`（1080p）**，NVAPI 核内合计为 **`-0.127027 / -0.230247 / -0.419533 ms`**。
   - **证据 ③（代数步骤下界与 `FB01` 局部副作用）**：要保持 E4M3 基本数值语义，去符号（`AND`）、饱和（`HMNMX2`）、缩放（`HMUL2`）、偶舍入（`SHF + LOP3 + LEA + IMAD`）、拼符号（`LOP3`）与字节收集（`PRMT`）这 9 条核心 SASS 已无可合并项；同时静态审计发现 `V2.9_fast` 虽然减少了 `FB01` 的指令数（`27,885 → 26,020`），但因 `ptxas` 在更短指令序列下提前调度了源寄存器读取，使 `FB01` 的 `MAX_STACK` 从 `96 B` 微增至 `104 B`（`STL/LDL` 从 `62/72` 变为 `64/70`）。

2. **硬判断二：当前 `V2.9_fast` 上唯一具备全档一致显著正敏感度的剩余缺口是 `Non-mapped Decode` 与解码临时寄存器池（`V2.9_fast − P1_V29`）**。
   - 在 `V2.9_fast` 基线上单变量移除 non-mapped 解码与 `vlh_t` 临时池（`V2.9_fast → P1_V29`），在**全部 12 个未插桩 pass 与全部 6 个 NVAPI pass（18/18）上 100% 显著加速**：
     - **未插桩四轮均值**：720p 下降 **`0.648250 ms (-10.97%)`**（`5.909750 → 5.261500 ms`）、900p 下降 **`1.105500 ms (-12.74%)`**（`8.675250 → 7.569750 ms`）、1080p 下降 **`1.732250 ms (-14.70%)`**（`11.787750 → 10.055500 ms`）；
     - **NVAPI 82 核合计**：720p 下降 **`0.598400 ms (-10.12%)`**、900p 下降 **`1.261133 ms (-14.24%)`**、1080p 下降 **`1.199770 ms (-10.70%)`**。

## 三、 针对剩余 `Non-mapped Decode` 缺口（`0.65 ~ 1.73 ms`）的下一刀具体靶点分析

既然 `V2.9_fast → P1_V29_NoDec` 仍表现出 `0.648 ~ 1.732 ms`（`11% ~ 15%`）的正向敏感度，我们将该缺口拆解为两个具体、可证伪的下一阶段（`PTX V3.0`）候选实验靶点，交由审计核验：

### 靶点 1：限制单 `mma_run` 解码临时寄存器池峰值（Pool Cap + Rematerialization），消除 `FB01` (`104 B`) 与 `FB04` (`88 B`) 的栈溢出
- **问题机制**：
  在当前 `v26/codegen.py` 中，一个非 `mapped` 源寄存器 `r` 本身只占 **1 个 `.b32` 寄存器**；但一旦在 `when[r] == i` 解码为 `(vlh_t0, vlh_t1)`，就会变成 **2 个 `.b32` 寄存器** 并一直保活到该 `mma_run` 内最后一次使用它的 `last[r]`。
  在 `FB01~03`（峰值 28 对 = **`56` 个 `.b32`**）、`FB04`（峰值 56 对 = **`112` 个 `.b32`**）、`FB05`（峰值 40 对 = **`80` 个 `.b32`**）中，大量权重/特征寄存器在 `mma_run` 开头被解码后跨越数十条 `HMMA` 持续占着双倍寄存器，直接导致：
  1. `FB01`（受 `.maxnreg 168` 限制以维持 `12 Warps/SM`）在 `V2.9_fast` 下产生 **`104 B STACK`（`64 STL / 70 LDL`）**（而在移除解码池的 `P1_V29` 下骤降至 `32 B STACK`、`5 STL / 5 LDL`）；
  2. `FB04`（`.maxnreg 255`）产生 **`88 B STACK`（`40 STL / 29 LDL`）**。
- **可验证方案**：
  - **方案 1A（临时池容量封顶 + 超额即时重解码 / Pool Budget Cap）**：为每个 Fatbin 设定解码缓存池上限 `MAX_CACHED_PAIRS`（例如在 `FB01` 中将 `56` 个 `.b32` 压至 `24~32` 个，在 `FB04` 中将 `112` 个压至 `48~64` 个）：在池满时，对跨距最长的操作数释放其 `(first, second)` 缓存并在下次使用时就地重解码（或仅分配 1 对共享 scratch 寄存器 `vlh_s0, vlh_s1` 即用即解），测试能否在不触发新 spill 的前提下将 `FB01` 的 `104 B STACK` 与 `FB04` 的 `88 B STACK` 压零并取得净提速。
  - **方案 1B（半相解码 / Phase-Split Decode）**：在一个 `mma` 站点的 `phase 0` 只解码低半字（4 条指令，占 1 个临时寄存器），用完立即覆写解码高半字送入 `phase 1`（对只使用 1 次的非 `mapped` 操作数，所需临时寄存器从 2 个减为 1 个，峰值直接减半！）。

### 靶点 2：审计并转化 `FB00`（32 个）与 `FB05`（4 个）中的 `pack_multidef` 候选为 `mapped` 直通
- **问题机制**：根据 `v27/source-summary.json`，全网活跃核中有 **36 个静态事件**（`FB00` 32 个、`FB05` 4 个）的根源已经是核内 FP8 打包指令（`cvt.rn.satfinite.e4m3x2.f16x2`），仅仅因为在函数内存在多个同名寄存器定义点（`pack_multidef`）而被 `ptx_mapped.py` 保守排除，退化成了 8 指令非 `mapped` 解码。
- **可验证方案**：对这 36 个 `pack_multidef` 站点做支配树 / 到达定义精确审计——若某个 `mma_run` 处的到达定义是唯一的（例如另一定义位于不支配该站点的互斥分支或后续基本块），即可安全放行进入 `mapped` 零 `PRMT` 直通，彻底消除这批站点的 8 指令解码与上游 9-SASS 打包！
