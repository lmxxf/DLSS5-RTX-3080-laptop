### 1.1 “达到可兑现性能上限”的严格系统边界定义
本报告所论证的“已达可兑现性能上限”，严格定义在以下 **原版 `nvngx_dlssnr.dll` (`v310.9.16.0`) 二进制改造工程边界** 之内（不作脱离该工程边界的空泛宣称）：
1. **Host 与模型资产不动**：不反编译或重写闭源 Host CPU 调度代码、不改变原版内嵌权重段与 Host-Device 函数参数 ABI、保持稳态每帧 82 次 NVAPI Kernel 发射序列与 Grid/Block 几何尺寸不变；

   - 速度门：候选必须在未插桩 `bench_sky.exe`（720p `sky`、900p/1080p `scene`，每进程 50 warmup / 80 iter，串行正反序 ABBA / BAAB）中，通过 **首轮（`first`）+ 复测确认轮（`repeat`）三档全部正反方向一致净提速**；

## 二、 为什么剩余的破坏性探针敏感度在当前边界下不可兑现？——四维微架构耦合与构造性反证

在 `V3.2`（48 次串行 `2×2` 探针）与 `V3.3`（84 次串行 `Shared / Global` 拆分探针）中，破坏性旁路探针给出了明确的非零敏感度读数：
- `V3.2` 去 Pack (`Base − P0`)：`+0.145500 / +0.102500 / +0.167250 ms`；去 Decode (`Base − P1`)：`+0.563500 / +0.992000 / +1.429500 ms`；
- `V3.3` 去 Decode 拆分：`Shared-Load`（2,320 事件）为 `+0.324500 / +0.500500 / +0.723250 ms`，`Global` 家族（3,528 事件，含 3,304 纯 Global 与 224 混合）为 `+0.414000 / +0.861750 / +1.204000 ms`，交互项为 `+0.197250 / +0.333750 / +0.438000 ms`。

为什么破坏性探针存在 `0.10 ~ 1.49 ms` 的差值，但上述 28 个保持语义（或满足 `>=50 dB` 质量门）的真实候选却无一能稳定兑现这笔时间？`V3.2 ~ V3.5` 的对照实验从四个正交维度给出了完整的微架构解释与构造性反证：

### 2.1 维度一：硬件驻留（Occupancy）受制于“寄存器悬崖 × 小 Grid 容量波次”双重封顶（分支 1 闭环）
1. **高波次大 Grid 核（`FB00..FB03`）已处于驻留帕累托前沿**：
   - `FB00 (C32)` 的 4 个主力核已在 `V2.7` 中通过 `.maxnreg 168` 升至 `12 CTA/SM (12 Warps/SM)`；`FB01 (C64)` 与 `FB02 (C128)` 全部为 `12 Warps/SM`；`FB03 (C256)` 为 256 线程大核（`190~203 regs`），强压 `168` 触发 Spill。
2. **低波次小 Grid 核（`FB04 C512` 与 `FB05 ViT`）跨阶无净收益**：
   - 在 `2000` 轮探针中，`P1_NoDec` 因直接删掉 4.5 万条解码指令使 `FB04/05` 的 7 个核自然降入 `<=168/128 regs`。
   - 但在真实保留解码的 `V3.2` 中，即便结合了 `split_up`，对这 6 个临界核施加 `.maxnreg 168/128` 时：
     - `publish` (`16 B STACK`)、`contract` (`8 B STACK`)、`expand` (`152 B STACK, 52/56 STL/LDL`)、`head` (`136 B STACK, 40/42 STL/LDL`)、`proj` (`144 B STACK, 42/47 STL/LDL`) 全部触发寄存器溢出；
     - 唯一实现 **零 Spill 自然跨阶（`162 regs, 0 B STACK, 2 → 3 CTA/SM`）** 的 `split_up_pool`（`cc_split_swin_16h_proj_pool_512_chained_fp8`），在 720p (`12×3×1 = 36 CTA`) 与 1080p (`16×5×1 = 80 CTA`) 下总块数本就不足以填满 `48 SM × 2 CTA = 96 CTA` 的单波次容量（`capacity waves = 1`），因此理论驻留上限从 `2 CTA/SM` 升至 `3 CTA/SM` 并未增加 720p/1080p 的实际并发 CTA 数，实测 720p/900p 依然方向变号（900p `-0.045%`）。

### 2.2 维度二：5-SASS Pack 已达 `sm_86` 单对转换下界，而双对 `Quad` 融合受制于 CFG 作用域与双源保活代价（分支 2 闭环）
1. **单对 `pack5`（5 条核心 SASS）无可删减**：
   - `HMNMX2 |R2|`（绝对值+448 饱和）、`HMUL2 2^-8`（指数偏置差对齐与 subnormal 移位）、`LEA 0x7f007f, 0x1`（左移腾符号位+舍入偏置）、`LOP3 0xb8`（符号位拼回）、`PRMT 0x4431`（抽取两路高字节）五步一一对应 IEEE 754 `f16x2 -> e4m3x2` 的五项代数操作；`P0_ZeroPack` 之所以快 `0.10~0.17 ms`，是因为它用单条 `cvt.u16.u32` 直接截断低 16 位（完全破坏数值并连带消除上游依赖链），而非存在少于 5 条 SASS 的有效 FP8 量化公式。
2. **双对拼接 `Quad` 在全网已无新增合法位点，且既有 `1,688` 对无稳定净收益**：
   - `V3.4` 的 `local_quad.py` 移除了旧版“全函数 `.b16` 出现次数 `==2` 及花括号深度 `==1`”的启发式限制，改用严格的同基本块最近定义 + CFG 全后继路径死变量分析（`dead_after`），结果证明：在全网 7,540 个 `mov.b32 %dst, {%lo, %hi}` 中，除 `FB01 (456) / FB02 (616) / FB03 (616)` 共 `1,688` 对外，**其余 5,852 处新增可融合对数严格为 `0`**（`FB00` 的 `mov` 是已编码字的反序拆装而非 `cvt` 量化输出；`FB04~06` 的半字定义跨越了基本块/循环边界，见 [v34/local-quad-audit.json](../ptx-patcher/v34/local-quad-audit.json)）。
   - 对这仅有的 `1,688` 对，我们在 `V3.3` 测试了 `quad_all` (`FB01+02+03`) 与 `quad_fb23` (`FB02+03`)，在 `V3.4` 测试了 `quad_fb1` (`仅 FB01`)：虽然 `quad_all` 与 `quad_fb1` 每两对省去 2 条 `PRMT` 并使 `FB01` 两核 `STACK` 从 `104/80 B → 96/72 B`，但由于 `quad` 要求 `vq_lo` 与 `vq_hi` 两个 32 位中间量同时跨兩段转换存活，改变了 `ptxas -O4` 的局部指令排程，在 `repeat` 确认轮中 `quad_all`（900p `-0.033%`、1080p `-0.148%`）与 `quad_fb1`（720p `-0.166%`、1080p `-0.111%`）均告回退。

### 2.3 维度三：非直通解码池峰值砍半（`112 → 28`）与 Spill 重解码均已被编译器/硬件平衡，外部 `ld.global` 解码不可消除（分支 3 闭环）
1. **外部 `ld.global` 源（`3,304` 纯 Global + `224` 混合事件）在不改 Host/权重文件的前提下物理上必须在线解码**：
   - 在 `v310.9.16.0` 的边界内，显存中的模型权重与跨核激活张量以 FP8 (`e4m3`) 存储，而 `sm_86` Tensor Core 仅支持 `.f16` 输入。因此，每个从 `ld.global` 读入的 32 位 FP8 词（含 4 个 E4M3 字节）在进入 `mma.sync` 前**物理上必须执行一次 `e4m3x4 -> 2 × f16x2` 解包**。
   - 每半边 4 条 SASS（`PRMT 0x9180/0xb3a2` + `LOP3 0x017f017f` + `SHF.L 7` + `HMUL2 0x5c005c00`）已将字节重排、清 bit 14、指数对齐与次正规数归一化压至 `sm_86` 指令集下限（`V3.2` 测试先移位后掩码的等价 `shift` 在 1080p 慢 `-0.225%`；测试将 `0x5c005c00` 直接作为 `mul.rn.f16x2` 立即数则被 `ptxas` 语法直接拒绝）。
2. **解码临时寄存器池从 `112/80/56` 压至 `28/28/28` 证明“池大小”已非真实瓶颈**：
   - `V3.2` 的 `Phase-Split JIT` 证实 `FB01~05` 峰值 `mma_run` 中单次使用操作数为 `0`（全部跨多条 K32 复用）；
   - `V3.3` 的 `Two-Pass Phase-Separated MMA` (`phase_pass`) 通过在同一依赖层内先跑完所有独立累加链的 `phase=0` 低半字、释放全部 `first` 后再复用同一批寄存器跑 `phase=1` 高半字，在不增加任何一条解码指令（半片段解码事件恒为 `11,696`）的前提下，将 `FB00..06` 的解码临时池峰值从 **`24/56/56/56/112/80/20` 砍半至 `12/28/28/28/28/28/6`**；
   - 然而实测 `phase_pass`（900p `-0.491%`、1080p `-0.050%`）与仅选 26 个零回退核的 `phase_guarded`（720p `-0.105%`、900p `-0.137%`）均未取得全档正收益；同时，针对 Spill 核的源码级不跨步缓存（`remat_spill / remat_fb1 / remat_qkv`）被 `ptxas -O4` 的 CSE 还原为相同的 `152,076` 条 SASS，而用 `noinline` 函数强制每次重算（`remat_call`）则暴慢 `67.6% ~ 72.8%`。这证明 `ptxas -O4` 在当前 `V2.6/V3.1` 池结构下已处于“缓存复用 vs 寄存器溢出”的最优平衡点。

### 2.4 维度四：静态 CFG 转发已达 `100%` 饱和，而 Shared Memory 2× FP16 耦合改写被 LSU 访存翻倍与新增 Spill 反杀（分支 4 闭环）
1. **静态 CFG 可达定义证明：全网 5,848 个 `non-mapped` 事件中，可安全免解码转发的漏网之鱼严格为 `0`**：
   - `V3.3` 对 144 个 `global_load + local_FP8_quantization` 混合事件（[v33/forwarding-audit.json](../ptx-patcher/v33/forwarding-audit.json)）与 `V3.4` 对 36 个 `pack_multidef` 事件（[v34/multidef36-audit.json](../ptx-patcher/v34/multidef36-audit.json)）完成了 100% 逐项 CFG 可达定义证明：**全部 180 项在到达 `mma_run` 入口时均存在两条不同运行时语义的可达定义（一条为真实显存/前序计算路径，另一条为越界 fallback pack 路径），唯一可达本地 pack 的事件数为 `0`**。
   - `V3.4` 在 MMA 解码之外找到的 36 个同线程 Shared 编码词返读（`shared_forward`）因必须保留非匹配 block 形状的回退分支，使静态非 NOP SASS 增加 `211` 条，1080p 实测慢 `-1.041%`。
2. **`V3.5` 构造性实测证明：将 Shared Memory 扩为 2× FP16 以消除读端解码，在微架构上是净亏损交易**：
   - `V3.4` 通过官方 `cuOccupancyMaxActiveBlocksPerMultiprocessor` 查明 `FB01~05` 的 Shared 容量翻倍本身不会降低 `CTA/SM` 驻留；
   - 据此，`V3.5` 真正实现了 `FB01~03` 的 7 个 Shared 2× FP16 耦合表示改写版本（含精确 `shadow`、精确原位 `inplace`、以及连写端 `pack5` 和读端 `decode8` 一并省去的近似夹断 `fast_shadow / fast_inplace`），并在 192 次串行运行中测出了決定性的微架构反证：
     - **代价一（Shared 访存指令与带宽翻倍）**：原本每 16 个通道只需 1 条 `st.shared.v4.u32`（16B）写入和 1 条 `ld.shared.v4.u32`（16B）读出；改为存储 16-bit `f16` 后，每个读写点必须拆为 **2 条 16B `v4.u32` 指令**（Shared 带宽需求与 LSU 管线发射数直接翻倍），导致 `fb1_exact_shadow` / `fb1_exact_inplace` 的总非 NOP SASS 反而从 `152,076` 暴涨至 `153,591` / `154,244`（净增 `+1,515` / `+2,168` 条）！
     - **代价二（双倍宽度 `f16x2` 向量提前驻留引爆零 Spill 核栈溢出）**：在原本 `164~168 regs`、`0 B STACK` 的 `FB02 (C128)` 上，从 Shared 直接读出双倍数量的 `f16x2` 寄存器使寄存器压力瞬间越过 `168 regs` 悬崖，导致 `fb2_exact_shadow` 的全网 `STL/LDL` 从 `107/108` 飙升至 **`176/163`**！
     - **决定性判据（即便同时省掉写端 `pack5` 与读端 `decode8` 依然变慢）**：在 `fb1_fast_inplace` 中，我们不仅省掉了读端解码，还省掉了写端的 `pack5` 量化（使全网 `PRMT` 从 `19,861` 降至 `18,794`、`STL/LDL` 从 `107/108` 降至 `102/102`、总非 NOP SASS 降至 `151,649`），但在三档串行 ABBA 实测中，720p (`-0.407%`) 与 1080p (`-0.379%`) 两个方向依然一致变慢！
   - **物理机制结论**：在 `sm_86` 上，用 **8-bit FP8 充当 Shared Memory 跨线程转置/交换的压缩传输格式**（1 条 `STS.128` + 1 条 `LDS.128` + 寄存器内 ALU 解包），其综合延迟实际上**优于**用 16-bit FP16 传输（2 条 `STS.128` + 2 条 `LDS.128` + 双倍 Shared  بانک冲突/带宽压力 + 双倍向量寄存器驻留压力）。原版内核将跨线程交换设计在 FP8 字节域，本身就是带宽与寄存器容量的结构性权衡，而非可免费消除的冗余。

## 三、 终局结论与工程建议

1. **搜索树完备性结论**：
   在原版 `nvngx_dlssnr.dll` (`v310.9.16.0`) 封存 Host 与权重 ABI 的工程边界下，围绕 `PTX V3.1_pack5` 建立的 `K-Search` 四大候选分支（**分支 1 驻留跨阶、分支 2 Pack 与 Quad 融合、分支 3 Decode 池/重排/重算/算术、分支 4 CFG 转发拓宽与 Shared 2× FP16 耦合表示**）均已完成 `K = 3` 轮构造性实现与串行配对验证（共 34 个编译版本、1,158 次独立进程运行），**剩余 `Open` 分支数严格为 `0`**。
2. **物理与微架构上限结论**：
   - 破坏性探针（`P0_ZeroPack`、`P1_NoDec`）测得的毫秒级差值，分别受制于 **5-SASS IEEE 754 量化代数下界**、**双源 `Quad` 寄存器保活排程代价**、**外部 `ld.global` FP8 权重/激活在无硬件 FP8 的 `sm_86` 上必须在线执行 4-SASS/half2 解码的指令集硬约束**、以及 **Shared Memory 扩为 2× FP16 时 LSU 16B 访存指令/带宽翻倍与寄存器压力反噬的微架构权衡**。
   - 上述四重物理与微架构边界相互咬合，使得在当前非侵入式 PTX 二进制修补范式下，任何试图进一步压减某单一静态指标（如砍半虚拟解码池、融合局部 `Quad`、或将 Shared 扩为 FP16 消除解码 `PRMT`）的改写，都会在另一条硬件管线（LSU Shared 带宽、`STL/LDL` 局部栈溢出或跨链指令排程）上付出更高或相等的代价。
3. **停工裁决请求**：
   综上，**`PTX V3.1_pack5`（`v0.3.0`，SHA256 `1190121f18a03080352fcec5d7a0b79ef47da0bb8ef2e00063e3b6999ff65c86`，研发配对 `5.75 / 8.42 / 11.35 ms`、低温评估 `5.62 / 8.38 / 11.07 ms`）确已达到当前 `nvngx_dlssnr.dll` PTX 改造范式下的可兑现性能上限**。现按《355.md》第四步规程提交本报告及全套 `v32~v35` 客观数据表请闇（`wE:p1`）执行 De-anchoring 独立审稿：若闇核验数据与论证无漏洞并认可该收官结论，本项目 PTX 优化主线即正式停工收官；若闇仍能指出任何未闭合的数据漏洞或可兑现的新分支，主脑将无条件重开搜索树继续迭代。
