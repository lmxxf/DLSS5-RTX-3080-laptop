## 一、`PTX V2.6` 突破成果与全阶段演进对照

在上一轮（`20261027-2214`）审核中，基于 `V2.5` 插桩数据确认了一个关键事实：在 `FB00`（1080p）的 `43,001,348` 个 MMA 解包对中，非 `mapped`（FP8 编码输入）仅占 **`29.98%`**（`12,892,128` 对），而 **`mapped`（由原生 `f16x2` 寄存器 `low, high` 打包的激活特征）占 `70.02%`（`30,109,220` 对）**。

据此实现的 **`PTX V2.6`** 将线程内 K32 的 4 字节拆解方式从 `V2.0~V2.4` 的偶奇拆解（`{byte0,byte2}` + `{byte1,byte3}`）切换为 **线程内 Low/High 半字拆解（`{byte0,byte1}` + `{byte2,byte3}`）**：
- **对 `mapped` 操作数**：直接将原生 `(low, high)` 寄存器填入两条 `mma.sync.aligned.m16n8k16` 操作数槽位，不分配解包临时寄存器对，不发射 `prmt 0x5410 / 0x7632`。全网 `FB00~06` 累计消除 **`21,712` 条静态 `mapped` PTX `PRMT`**（对应既往 `V2.5` 插桩口径下 `FB00` 1080p 单帧约 `60,218,440` 次 `mapped` PTX `PRMT` 生成事件，且实际模型中需提前 `mov` 备份的覆写冲突为 `0` 处）。
- **对非 `mapped` 操作数**：采用 `prmt 0x9180 / 0xb3a2` 提取低/高半字及符号，后接 `and 0x017f017f`、`shl 7`、`mul.rn.f16x2`，保持 8 条 PTX 指令不变。

## 二、`V2.6` 之后：距离理论下限还有多远？剩余算力缺口与待验证靶点评估

以 `V2.5` 软件插桩实测的 `FB00 / 04 / 05` MMA 语义等价工作量加上 `FB01 / 02 / 03 / 06` 静态补估的混合参考（720p `59,311,872` 条 `HMMA`、1080p `118,357,376` 条 `HMMA`，在假定 `1695 / 1605 MHz` 与 `4 SM-cycles/HMMA` 下的理想纯 Tensor Core 时间参考值为 **720p `2.916 ms` / 1080p `6.145 ms`**），对比当前 `V2.6` 的实测总耗时（**720p `5.980 ms` / 900p `8.722 ms` / 1080p `11.463 ms`**），两者之间的算术差额为：
- **720p**：`5.980 - 2.916 = 3.064 ms`
- **1080p**：`11.463 - 6.145 = 5.318 ms`

> **边界声明**：该差额不能简单等同于“可全部回收的浪费”，因为它同时包含了：① 无法 100% 被 Tensor Core 隐藏的辅助 SASS 指令（非 `mapped` FP8 解包、函数尾 `SWAR` 打包、Swin/ViT 激活函数与归约、地址计算）；② Global/Shared 内存延迟与跨 CTA `tilesync/wait` 同步依赖；③ `FB04/05/03` 小 Grid 在 48 个 SM 上的驻留与波次未满载；④ 实际运行频率与假定频率的偏差。

但在 **`V2.6` 刚刚改变了寄存器压力分布（活跃 C32 核降到 `196~200` regs、`FB01` 最大 `STACK` 从 `224 B` 降到 `104 B`）并重写了 MMA 布局** 之后，以下几个具体的结构性问题尚未在 **`V2.6` 新基线** 上得到验证或闭合：

### 靶点 1：`V2.6` 大幅降低 `FB00 / FB01` 寄存器与栈溢出后，`.maxnreg` 与条件因子（`A` / `B`）是否出现新的组合收益？
1. **`FB00 (C32)` 寄存器降至 `196~200` 后的驻留台阶**：
   - 在 `V2.4` 中，`pre_block / inpview / ds_wait / outview` 占 `231~236` 个寄存器（每块 1 Warp = 32 线程，每块需 `32 × 240 = 7,680` regs，65,536 寄存器池最多驻留 **8 Warps/SM**）；
   - 到了 `V2.6`，这 4 个活跃 C32 核的寄存器已自然降至 **`196 ~ 200`**！而在 `sm_86` 上（65,536 regs/SM，分配粒度 8 regs/lane = 256 regs/warp）：
     - `200` regs/lane → 每 Warp 占 `6,400` regs → `floor(65536 / 6400) = 10 Warps/SM`；
     - `192` regs/lane → 每 Warp 占 `6,144` regs → `floor(65536 / 6144) = 10 Warps/SM`；
     - `184` regs/lane → 每 Warp 占 `5,888` regs → **`floor(65536 / 5888) = 11 Warps/SM`**；
     - `168` regs/lane → 每 Warp 占 `5,376` regs → **`floor(65536 / 5376) = 12 Warps/SM`**！
   - 更值得注意的是：`FB01 (C64)` 在 `V2.6` 下 `.maxnreg 168` 的最大 `STACK` 已从 `224 B` 减半至 `104 B`（活跃 `ds/inpview` 仅 `64 B`），此时若将 `FB01` 微调至 `176 / 184 / 192` 或结合 `A/B` 减少临时变量，其 spill 与驻留权衡点可能已不同于 `V2.4`！
2. **`V2.4` 中暂未默认启用的因子 `A`（独立 `FP8_UP` 7→5，静态减少 `1,878` 条 SASS）与因子 `B`（`+0x603f603f` + `1,688` 对 `prmt 0x6420` 四字节融合打包）在 `V2.6` 上的表现**：
   - 在 `V2.4` 中，`ABC` 组合虽然三档均赢 `V2.3`，但因 `AB` 对 `C` 的增量在部分方向有波动而未默认打开；如今 `V2.6` 已经消除了 21,712 条 `mapped` `PRMT`，在更干净的 `V2.6` 基线上重新测试 `A` 与 `B`（特别是 `FB01/02/03` 中那 `1,688` 对四字节融合打包能否进一步压低 `FB01` 仅剩的 `64~96 B` spill），尚未验证。

### 靶点 2：`V2.6` 中非 `mapped` 解包与残留 `pack_multidef` 的进一步压缩空间
1. **非 `mapped` 解包的高半字 `second`（`byte2, byte3`）**：
   - 在 `V2.6` 的 `lowhigh8` 中，`second` 取的是 `register` 的高 16 位 `{byte2, byte3}`（位于 bit `16..23` 与 bit `24..31`）。
   - 注意：`byte3` 的符号位本来就在 `bit 31`！虽然 `V2.5` 证明了用 `SHR` 替代 `PRMT` 会增加 `SHF.R.U32.HI` 而回退，但在 `V2.6` 中，同一个编码寄存器 `register` 的 `first`（`0x9180`）和 `second`（`0xb3a2`）是否可以通过改变解包指令顺序或常量复用进一步缩短依赖链？
2. **未被 `mapped` 转发覆盖的编码源（特别是 `FB01 / FB02 / FB03` 与 `FB04 / FB05`）**：
   - 为什么在 `FB01~FB05` 中，最大解包临时寄存器池峰值（`56 / 56 / 56 / 112 / 80`）在 `V2.6` 下完全没有下降？
   - `v26/README.md` 第 68 行指出：**“因为这些最大 run 受非 `mapped` 输入限制。”**
   - 这揭示了一个极其关键的不对称现象：在 `FB00` 里 `mapped` 占了 `70%`（所以 `FB00` 临时池从 `40` 降到了 `24`，寄存器降了 30 多个）；但在 **`FB01~FB05` 的最大 MMA run 里，大量激活或输入仍然走的是非 `mapped`（即先 `cvt.e4m3x2.f16x2` + `mov.b32 {rs0, rs1}` 打包成 FP8，或者从 Shared Memory 读出 FP8，再在 MMA 前用 8 条指令解包并占 2 个临时寄存器）**！
   - 为什么 `FB01~FB05` 的那些 MMA run 里 `mapped` 命中率低？是因为它们的 `cvt` + `mov.b32` 位于循环头/分支外被 `ptx_mapped.py` 的作用域/支配规则过滤掉了，还是因为它们确实是从 Shared Memory (`ld.shared`) 加载的权重/特征？
   - **这需要先做一个精确审计**：在 `FB01 ~ FB05` 的所有非 `mapped` MMA 操作数中，到底有多少比例来自 `ld.shared / ld.global`（真外部 FP8 数据），有多少比例其实来自同函数内的 `mov.b32 {rs0, rs1}` 却被当前 `ptx_mapped.py` 拒绝了？

### 靶点 3：获取 `V2.6` 的最新逐 Fatbin 真实耗时分布
- 目前我们引用的逐 FB 耗时表（`6.127 / 11.861 ms`）仍是 `V2.3` 阶段对 `V2.2` 基线采集的；经历了 `V2.3`、`V2.4`、`V2.6` 三轮迭代（尤其是 `V2.6` 砍掉 21,712 条 `mapped` `PRMT`）后，`FB00 ~ FB06` 各模块各自快了多少毫秒、现在最新的第一瓶颈模块是谁，尚未用 `bench_profile.exe` 采集 `V2.6` 的逐 FB 账本。
